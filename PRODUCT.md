# Product

## Platform

web

## Users

**Primary: the author**, a technical writer working on documentation
information architecture. Fabula is a personal tool first — built for
his own IA work — and open-sourced so peers benefit from it.

**Secondary, and real:** the technical writing community he publishes
to. Docs IA owners and tech writers restructuring a site's navigation;
docs engineers reviewing or proposing IA changes; anyone who inherits a
large TOC and has to understand it fast.

**A third audience uses the output without using the app:** reviewers
and stakeholders who are shown a structure they do not know, to
understand or approve it. They never load a TOC themselves.

## Product Purpose

Documentation IA lives in TOC files (`toc.yml`, `mkdocs.yml` nav,
frontmatter, `toctree` directives) that are edited as text: deeply
nested config where "move this subtree under that section" means
error-prone cut-and-paste, and where nobody can see the shape of the
whole navigation at once. IA work is inherently spatial and
comparative; the tooling is neither.

Fabula renders a TOC as cards on an infinite canvas so its structure
can be seen whole, restructured by dragging, and written back to the
source file losslessly.

Success is that a real restructure of a real docs site happens faster
and with more confidence than editing the file by hand — and that the
resulting structure can be shown to someone else and understood.

## Positioning

An **upstream IA planning tool**, not a help-authoring tool. It edits
navigation structure, never page content, and it is an editor for
_someone else's_ file format rather than a new source of truth.

**It is not a commercial product and should not be designed as one.**
The license (AGPL-3.0) was chosen deliberately to prevent the work being
taken and sold. Language elsewhere in the repo about "differentiation",
"incumbents" and a "long-term stickiness play" toward DITA/MadCap
describes ambitions for capability, not a business model: there is no
pricing, no upsell path, no growth target, and future work should not
invent one.

It is, however, published under the author's professional name in a
field where he is a known voice. Credibility to technical-writing peers
is a real constraint — the tool reflects on its author.

## Operating Context

Three usage occasions are all real. In priority order:

1. **A big restructure or IA audit.** Episodic and high-stakes — a
   replatform, a merger of two docs sets, a navigation overhaul. Used
   intensely for a stretch, then not for months, so **sessions usually
   start cold**: the user is re-orienting to both the tool and the
   corpus.
2. **Producing a review artifact.** Showing a structure to people
   unfamiliar with the corpus, to explain or get agreement on an IA
   change. The audience's understanding is the deliverable.
3. **Ongoing docs upkeep.** Returned to as docs grow, for smaller
   edits. Genuine but secondary.

Work happens on a desktop, against a checked-out docs repo, and ends in
a git commit the user makes themselves. Corpora are large and real:
the reference corpus (`godot-docs`) is 1601 files with 1594 documents
reachable from its nav.

## Capabilities and Constraints

- **Round-trip fidelity is a hard requirement.** An unchanged document
  exports byte-stable; an edit changes only what the user changed.
  Properties the app does not understand are preserved verbatim.
- **Supported systems:** DocFX `toc.yml`, MkDocs `nav:` (single-file
  formats, round-trip through Export); Just the Docs frontmatter and
  Docusaurus autogenerated sidebars (folder-based, written back as
  reviewed per-file edits or a `.patch`); Sphinx `toctree`
  (**write-back shipped, moves-only** — an entry line relocates between
  toctree blocks, possibly across files; nothing else is rewritten.
  docs/19).
- **Zero infrastructure.** Pure client-side SPA. No accounts, no server,
  no analytics; nothing leaves the browser. Sessions persist to
  localStorage only. Deployable as static files.
- **AI reorganize is optional and bring-your-own-key.** Only topic
  titles are sent; paths, identifiers and format-private data never
  leave. Results open as a new tab and never overwrite the original.
- **A desktop app, by design (ruled 2026-08-18).** The two-dimensional
  canvas exists so a human brain can take in a table of contents as a
  MAP rather than one long list, and a map needs a screen wide enough
  to show the shape whole. On a small screen that purpose is not
  degraded, it is defeated — so there is no "acceptable read-only
  mode" to maintain and no mobile work, ever. A designed absence with
  its reason, not a deferral. Hover is a first-class input.
  Accessibility is explicitly NOT relaxed by this ruling: keyboard
  reachability holds, keyboard-driven drag stays on the backlog, and
  no finding may be carried by hover alone. Ordinary information may
  live in a tooltip alone — hover is a first-class input, and that is
  what first-class means.
- **Not in scope:** editing page content, cross-format conversion,
  real-time collaboration, accounts, cloud sync.
- **Open decision — a shareable static output.** Reaching reviewers who
  never open the app _is_ in scope as a capability, but nothing
  implements it yet. Future work should treat this as a real gap to
  close, not as settled either way.
- **Open decision — surfaces beyond the app.** Whether a landing page or
  a docs/help site exists is undecided; today the README and the
  repository are the only front door.

## Product Principles

1. **The file is the truth.** The app is an editor for someone else's
   format. Fidelity outranks convenience; if a change cannot be written
   back faithfully, it should not be offered.
2. **Legible to a stranger.** The second-priority job is explaining a
   corpus to someone who has never seen it. A view that only makes
   sense to the person who built it has failed that job.
3. **Assume a cold start.** Episodic use means most sessions begin
   without recall of either the tool or the corpus. Orientation is
   recurring work, not a one-time onboarding problem.
4. **Undo makes bravery cheap.** Every structural operation is undoable,
   and the change is shown, so restructuring can be exploratory rather
   than careful.
5. **Contribution over breadth.** Support for a new documentation system
   is one adapter file, one fixture and one registry line. Growth comes
   from that staying true.
6. **A limit may cost detail, never shape.** The first job is seeing the
   information architecture whole, so any budget — storage caps, render
   depth, payload bounds — may reduce what is shown _about_ a node, but
   must never silently drop a branch or fold a subtree out of the tree.
   Truncating detail leaves the reader with less; truncating shape leaves
   them with a confident picture that is wrong, which is worse than
   refusing outright. When a limit genuinely cannot be met, refuse and
   say why. This is the axiom behind loading a whole site by default
   rather than a convenient subtree.

## Accessibility & Inclusion

**Best-effort; no standard is committed.** No WCAG conformance is
claimed or targeted, and future work must not claim one. What exists
today: labelled controls, focus handling, keyboard reachability, a
documented keyboard map, and reduced-motion support in the animation
layer.

Known gap, recorded rather than promised: the core interaction is drag,
and keyboard-driven drag is unbuilt (backlog in `docs/08`). Anyone who
cannot drag cannot currently restructure.
